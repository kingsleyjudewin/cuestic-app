# Production Deployment Guide

Backend (Flask, Docker) → **Render** (Ohio) · Database → **Neon** PostgreSQL (us-east-2) ·
Files → **Firebase Storage** (or a Render Disk) · Web app → **Vercel** · Android APK → **GitHub Actions**.

```
 Android APK ─┐                       ┌─> Neon Postgres (pooled, us-east-2)
              ├──HTTPS──> Render API ─┼─> Firebase Storage (uploads)  ·  FCM (push)
 Vercel web ──┘   (1 worker, 12 thr)  └─> Gemini / Groq (AI) · Google Drive (optional)
```

## 0. Do these first (security)

1. **Secure the leaked accounts.** `start.md` (public repo) contained real passwords, and the code had a
   hard-coded admin backdoor (now removed). 38 of 61 active accounts still use one of those passwords.
   Follow [§8 Mandatory password change and leaked passwords](#8-mandatory-password-change-and-leaked-passwords).
   Git history still contains them, so treat them as compromised even after the files are cleaned.
2. **Consider making the GitHub repository private.** `scripts/volunteers_input.json` and
   `database/seeds/volunteers_input.json` contain real student names and phone numbers.
3. Never commit: `.env`, the Firebase service-account JSON, `*.jks` keystores, `key.properties`,
   `instance/rotated_credentials_*.csv`. All are in `.gitignore` / `.dockerignore`.

## 1. Render (backend)

> **Currently configured for Render's FREE plan** (`render.yaml`): 512 MB RAM, the service sleeps after
> 15 minutes without traffic (first request then takes ~30–60 s), attendance OCR is turned off
> (`ENABLE_OCR=false`, the endpoint answers 503 `OCR_DISABLED`), reminders only run while awake, and there is
> no pre-deploy step — run `flask db upgrade` against Neon yourself before deploying a new migration.
> To upgrade: set `plan: standard`, `ENABLE_OCR=true`, restore `GUNICORN_THREADS=12`, `DB_POOL_SIZE=10`,
> `MAX_CONCURRENT_HEAVY_JOBS=2` and add `preDeployCommand: flask db upgrade`.

### Create the service
1. Render Dashboard → **New → Blueprint** → select this repository. Render reads `render.yaml`.
2. Confirm: runtime **Docker**, region **Ohio** (same AWS region as Neon), plan **Standard (2 GB)**.
   * Free/Starter (512 MB) are **not sufficient**: idle ≈ 160–230 MB, one OCR run peaks ≈ 630 MB,
     load test with OCR peaked at 659 MB.
3. Fill in the `sync: false` variables when prompted (table below). `SECRET_KEY` is generated.
4. **Secret File** (Service → Environment → Secret Files → Add):
   * Filename: `firebase-service-account.json`
   * Contents: the Firebase Admin SDK JSON (Firebase Console → Project settings → Service accounts →
     Generate new private key). Render mounts it at `/etc/secrets/firebase-service-account.json`,
     which `GOOGLE_APPLICATION_CREDENTIALS` points to.
5. Deploy. Render runs `flask db upgrade` (pre-deploy, upgrade-only) then starts
   `gunicorn -c gunicorn.conf.py wsgi:app`. Health check: **`GET /health`** (checks the DB).

### Before enabling reminders on the existing database (once)
The production DB has 0 reminder rows, so the first scan would push ~125 "overdue" notifications for old
assignments. Record them silently first (Render → Shell):
```bash
flask reminders-scan --no-notify
```
Then keep `ENABLE_BACKGROUND_SCHEDULER=true`. Scans run every 15 min, take a database lock (safe with
several processes/instances) and each reminder is delivered exactly once.

### Local Docker run (same image as Render)
```bash
docker build -t cuestic-api .
docker run --env-file .env.production -p 8080:8080 \
  -v "$PWD/firebase-service-account.json:/etc/secrets/firebase-service-account.json:ro" cuestic-api
curl http://localhost:8080/health
```

### Scaling notes
* One worker × 12 threads on 1 CPU: **≈ 300 req/s** sustained in testing. Teams/events/members/chat caches are
  in-process, so stay at `WEB_CONCURRENCY=1` and `numInstances: 1` unless those caches are moved to Redis.
* Auth tokens and reminder scans are already multi-process safe.

## 2. Neon (database)
* Use the **pooled** connection string (`-pooler` host) with `sslmode=require` for `DATABASE_URL`.
* Schema is at the latest Alembic revision (`e4f5a6b7c8d9`). Deploys only run `flask db upgrade`; nothing
  drops or resets data. Before a deploy that adds a migration, create a Neon branch as a restore point:
  Neon Console → Branches → Create branch from `main`.
* Free-tier compute scales to zero after inactivity; the first request after that takes ~1–6 s extra.
  Disable "scale to zero" on a paid plan if that matters.

## 3. Firebase Storage (persistent uploads)
Render's filesystem is wiped on every deploy/restart, so uploads must go to Firebase Storage
(or a Render Disk, see `STORAGE_LOCAL_ROOT`). Firebase Storage is **not enabled yet** for
`club-management-cuestic` (checked: bucket unreachable).

1. Firebase Console → **Build → Storage → Get started**. New default buckets
   (`<project>.firebasestorage.app`) require the **Blaze (pay-as-you-go)** plan; usage for ~50 users fits
   in the free quota.
2. Location: `us-east1` (closest to Ohio).
3. Security rules — the backend uses the Admin SDK (bypasses rules); block all direct client access:
   ```
   rules_version = '2';
   service firebase.storage { match /b/{bucket}/o { match /{allPaths=**} { allow read, write: if false; } } }
   ```
4. IAM (Google Cloud Console → IAM): the service account in the JSON needs
   **Storage Object Admin** on the bucket. For signed download URLs also grant
   **Service Account Token Creator** on itself. The default `firebase-adminsdk-…` account normally has
   both already; check in IAM if uploads or downloads return permission errors.
5. Set `FIREBASE_STORAGE_BUCKET` and the Secret File on Render (§1). Logs show
   `Firebase Storage connected to bucket: …` on the first upload.
6. Migrate files that were saved locally during development (run locally with the same `.env`):
   ```bash
   .venv/bin/python scripts/migrate_to_firebase_storage.py           # keeps local copies
   ```
   Object keys are identical in both backends, so database rows need no changes.

**Alternative without Firebase:** add a Render Disk (Service → Disks, mount path `/var/data`, 1 GB) and set
`STORAGE_LOCAL_ROOT=/var/data/storage`. Works only with a single instance.

## 4. Vercel (Flutter web)
The site is built by GitHub Actions (`.github/workflows/flutter-web-vercel.yml`) and uploaded as static files.

1. `npm i -g vercel` → in an empty folder: `vercel login` → `vercel project add cuestic` (or create the project in
   the dashboard, framework preset **Other**, no build command).
2. Get IDs: `vercel link --project cuestic` then read `.vercel/project.json` (`orgId`, `projectId`).
3. Create a token: Vercel → Account Settings → Tokens.
4. GitHub repo → Settings → Secrets and variables → Actions:
   * Secrets: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`
   * Variables: `API_BASE_URL` = `https://<your-render-service>.onrender.com/api/v1`
5. Push to `main` (or Actions → *Flutter Web → Vercel* → Run workflow). The run summary prints the URL.
6. Put that URL in Render `CORS_ORIGINS` and redeploy the backend.

`vercel.json` provides SPA fallback (deep links / reloads never 404), `no-cache` for `index.html` and the
bootstrap/service-worker files, and caching for static assets. `scripts/postbuild_web.py` cache-busts the
bundle so users never run a stale version.

## 5. Android APK
Workflow: `.github/workflows/android-apk.yml` (manual run or push a `v*` tag).

### One-time: create the upload keystore (keep it forever — losing it means users must reinstall)
```bash
keytool -genkeypair -v -keystore cuestic-upload.jks -alias cuestic -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 cuestic-upload.jks > cuestic-upload.jks.b64
```
Store the `.jks` and its passwords in a password manager. **Never commit them.**

GitHub → Settings → Secrets and variables → Actions → Secrets:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | contents of `cuestic-upload.jks.b64` |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | `cuestic` |
| `ANDROID_KEY_PASSWORD` | key password |

and the variable `API_BASE_URL` (same as Vercel).

### Get the APK
* **Download link (recommended):** `git tag v1.0.0 && git push origin v1.0.0` → GitHub → *Releases* →
  `cuestic-v1.0.0-<build>.apk`. Share that release page link.
* Or Actions → *Android release APK* → Run workflow → run page → **Artifacts** → `cuestic-android-apk` (30 days).

The workflow fails (instead of producing a debug-signed APK) when signing secrets are missing, and verifies the
certificate is not the debug key. Version name = tag (or `pubspec.yaml`), version code = run number.

### Local release build
```bash
cd frontend
cat > android/key.properties <<EOF   # git-ignored
storeFile=/absolute/path/cuestic-upload.jks
storePassword=...
keyAlias=cuestic
keyPassword=...
EOF
flutter build apk --release --dart-define=API_BASE_URL=https://<service>.onrender.com/api/v1
```
Release builds are HTTPS-only (network security config); debug builds may use `http://` to local servers and
keep the "Server API URL" field on the login screen. A release build compiled without a valid HTTPS
`API_BASE_URL` shows a configuration-error screen instead of starting.

| Scenario | Throughput | p50 | p95 | 5xx | Peak memory | DB conns |
| --- | --- | --- | --- | --- | --- | --- |
| 10 users, no think time | 305 req/s | 30 ms | 55 ms | 0 | — | — |
| 25 users, no think time | 279 req/s | 89 ms | 125 ms | 0 | — | — |
| 50 users, no think time | 301 req/s | 157 ms | 245 ms | 0 | 367 MB | 13 |
| 50 users, ~2 s think time (realistic) | 25 req/s | 4 ms | 10 ms | 0 | — | — |
| 50 realistic users + 4 continuous OCR clients | 19 req/s | 9 ms | 40 ms | 0 | — | — |

* Single attendance OCR (2-page PDF, 50 rows): 6–9 s. Queued OCR requests wait; beyond the limits they get 503.

* Add ~1–2 ms per DB query for Render↔Neon and the user's network round trip (~250 ms from India to Ohio).

## 8. Mandatory password change and leaked passwords

Every account except the single `admin` role must set a new password. The **server** enforces it: while
`users.password_change_required` is true, every API call except `GET /auth/me`, `POST /auth/logout`,
`POST /auth/change-password` (and the two legacy `/research/auth/*` password endpoints used by already
installed APKs) returns **403 `PASSWORD_CHANGE_REQUIRED`**. The web app and the new APK show a blocking
"Create Your New Password" popup; older APKs show their existing first-login password screen.

New passwords must have ≥ 12 characters with upper case, lower case, a number and a special character,
must differ from the current one, must not contain the username, and must not be on the common/leaked list.
A successful change signs out every other session and issues a new token.

> **Why both steps below are needed.** Forcing a change alone does not protect an account whose password is
> public: whoever signs in first with the leaked password can choose the new one. Accounts still using a
> leaked password must first get a random temporary password (step 3), handed to the owner privately.

### Rollout (in this order)
1. **Back up Neon:** Neon Console → Branches → *Create branch* from `main` (e.g. `pre-password-reset`).
   This is the rollback point for data.
2. **Deploy the backend.** Render runs `flask db upgrade`, which adds `password_change_required`
   (default `false`) and `password_changed_at`. Nothing changes for users yet.
3. **Block and rotate the leaked passwords.** Put the leaked passwords (one per line) in a file **outside the
   repository**, e.g. `/tmp/leaked.txt`. On your computer:
   ```bash
   flask password-hashes --input /tmp/leaked.txt --output /tmp/leaked_password_hashes.txt
   ```
   Upload `/tmp/leaked_password_hashes.txt` to Render as Secret File `leaked_password_hashes.txt`
   (`LEAKED_PASSWORD_HASHES_FILE` in `render.yaml` already points to it), so nobody can choose one of them again.
   Then on Render → Shell (upload `/tmp/leaked.txt` there temporarily, or run locally with Neon's `DATABASE_URL`):
   ```bash
   flask rotate-leaked-passwords --leaked-file /tmp/leaked.txt                    # dry run
   flask rotate-leaked-passwords --leaked-file /tmp/leaked.txt --confirm --output /tmp/new_passwords.csv
   ```
   Affected users get a random temporary password, all their sessions are revoked, and they are flagged.
   Distribute each temporary password privately; then delete the CSV and `/tmp/leaked.txt`.
4. **Preview** the remaining accounts:
   ```bash
   flask require-password-change
   ```
   On a copy of the current production data this reports **60 accounts** (`faculty_coordinator` 24,
   `member` 28, `president` 1, `student_researcher` 4, `team_leader` 3; the one `admin` excluded).
   Equivalent SQL: `SELECT role, count(*) FROM users WHERE role <> 'admin' AND NOT password_change_required
   AND password_changed_at IS NULL GROUP BY role;`
5. **Apply:** `flask require-password-change --confirm`. Safe to re-run: accounts that already changed their
   password (`password_changed_at` set) or are already flagged are skipped. Profiles, roles and passwords are not touched.
6. Deploy the web app (Vercel) and publish the new APK (tag `v1.x.y`). Old APKs keep working: they show
   their existing password screen, and the server blocks everything else regardless of the app version.
7. **Verify:** admin signs in and works normally; a president/member account gets the popup and every other
   screen fails with 403 until the change; after the change the old password and old sessions are rejected.
8. Track progress: `SELECT role, count(*) FILTER (WHERE password_change_required) AS pending, count(*) AS total
   FROM users GROUP BY role;`

### Rollback
* Undo the requirement for accounts that have not changed yet: `flask require-password-change --revert`
  (preview) then `--revert --confirm`. Accounts that already set a new password keep it.
* Schema: `flask db downgrade` removes only the two new columns. Data rollback: restore the Neon branch from step 1.
  Rotated passwords cannot be "un-rotated" except by restoring that branch.

### New accounts
Accounts created by the president (`/members/account`), imports, faculty adding a student, or a password
reset by an administrator/faculty are flagged automatically: the person must replace that password at first
sign-in. Invitation links (`/auth/setup-password`) let users choose their own password, which is not forced again.

To remove the passwords from Git history as well (optional, rewrites history — coordinate with everyone who
cloned the repo first): `git filter-repo --replace-text replacements.txt`, then force-push and ask
collaborators to re-clone. Rotation is what actually protects the accounts.

## 9. Troubleshooting
| Symptom | Cause / fix |
| --- | --- |
| Web app: "Failed to fetch" / CORS error | `CORS_ORIGINS` on Render must exactly match the Vercel URL (scheme, no trailing slash) |
| Upload returns 503 `STORAGE_UNAVAILABLE` | Firebase Storage not enabled / bucket name wrong / Secret File missing (see §3) |
| 503 `SERVER_BUSY` | Too many simultaneous OCR/report/AI jobs; retry, or raise `MAX_CONCURRENT_*` on a bigger plan |
| 503 `PDF_TOOL_MISSING` | Image built without poppler — use the repository `Dockerfile` |
| App shows "App configuration error" | APK/web built without a valid HTTPS `API_BASE_URL` |
| Everything returns 403 `PASSWORD_CHANGE_REQUIRED` | Expected until that user sets a new password (§8). Admin is never affected |
| Instance restarts during OCR | Plan too small (needs 2 GB) |

## Visitor (demo) account

A shared login that sees the admin screens on an **empty, read-only** workspace. The server enforces this (see
`app/utils/visitor_mode.py`): every database read in a visitor request is filtered to nothing (except the visitor's
own user row), every write answers `403 VISITOR_READ_ONLY`, and the in-memory caches are bypassed, so no real
data is ever served to it. The app shows a yellow "Visitor mode" strip.

Which usernames count as visitors is set by `VISITOR_USERNAMES` (default `visitor`, comma-separated). Create or
reset the account against the production database once (Render free plan has no shell, so run it locally with
`DATABASE_URL` pointing at Neon):

```bash
DATABASE_URL='postgresql://…neon…' FLASK_APP=wsgi.py flask create-visitor --password 'Visitor@2026'
```

The command refuses usernames that are not in `VISITOR_USERNAMES`, so it can never create a real admin by
mistake. To withdraw visitor access, deactivate the account or change its password with the same command.
